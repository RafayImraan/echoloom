# EchoLoom contract security gate

This is a source review backed by local compilation, Foundry tests, and Slither. It is not an independent professional audit. No contract has been deployed, no live transaction was tested, and no real funds should be used.

## Slither findings

The prior Slither run reported the following nine results. Its detector results are reproduced in `docs/VERIFICATION_REPORT.md`. The first seven below describe the initial source; fixes and current findings are identified explicitly.

User claims pay the claimant; only the owner-selected protocol-fee destination is arbitrary. This cannot spend another user's mapped credit. Failed calls revert, restoring state. ## Accounting and adversarial review

- Assets enter as stake principal, explicit reward funding, or tips. Mapping credits and `protocolFees` track tip liabilities separately. Forced ETH, if any, is surplus; there is no withdrawal path that can spend it against another account's credit.
- Stake principal is stored in `stakeOf`; immutable historical reward weight is stored in `stakeWeight`. Withdrawing principal leaves reward weight intact and `totalStake` remains the settlement denominator.
- `rewardPool` is a cumulative funded total, not a remaining-payout counter. Creator and curator each have one-time flags; supporter claims are one-time per account. Reverts roll those flags back. UI labels this field “Funded rewards.”
- Tests explicitly reject repeated creator and curator claims, and verify a rejecting reward recipient leaves both the supporter-claim flag and contract balance unchanged.
- For each post, creator + curator + supporter BPS are snapshotted and constrained to at most 10,000. Each allocation rounds down; claims can leave dust but cannot exceed the funded reward pool. Fuzzing covers varied stakes and funding amounts, including dust-sized values.
- Tips credit `msg.value - fee` to the creator and the fee to `protocolFees`. Fee is capped at 500 BPS. Only the owner can withdraw the protocol liability or change the fee; the recipient is owner-selected.
- Withdrawals clear state before `_pay`. A rejected receiver causes revert and restores state. Reentrant writes through the guarded withdrawal/claim paths fail. Other callbacks do not expose an unguarded payout or bypass role checks.
- `setPaused(true)` blocks new Looms, edits, posts, stakes, tips, and reward funding. Existing stake withdrawal, reward claims, creator earnings withdrawal, and protocol-fee withdrawal remain available. Tests exercise both sides.
- Deadline comparisons are consistent: stake/funding require `now < deadline`; claims/principal withdrawal require `now >= deadline`. Loom windows are bounded to 1 hour–30 days. Post creation now rejects timestamps that cannot safely fit both `createdAt` and `deadline` in `uint64`.
- Contract actions use constant-time mappings and no user-triggered loop. Reward distribution is claim-by-claim; one user's failure cannot block other users.
- No floating-point token arithmetic exists in the client; MON values use Viem `parseEther`/`formatEther` and `bigint`.

## Deployment configuration findings

The prior client let `NEXT_PUBLIC_ECHOLOOM_HUB` silently override generated metadata and did not confirm which chain its RPC served. It now fails closed if address, transaction, or block environment values conflict with the deployment artifact. Before a read or write it verifies RPC chain ID 10143, nonempty code at the hub, and a successful deployment receipt whose contract address and block match configuration. Manual setup requires all three public values: hub address, deployment transaction hash, and deployment block. The record script validates a Monad Testnet Foundry broadcast receipt before writing the artifact.

The deploy script checks chain ID 10143 before broadcast, requires the exact configured HTTPS Monad RPC URL, reads `DEPLOYER_PRIVATE_KEY` only through `vm.envUint`, checks at least 0.01 MON, and deploys the current no-argument constructor. Neither the private key nor any signing secret is placed in browser variables or deployment metadata.

## Upload and persistent activity additions

- The upload route accepts only allowlisted image/text MIME types and extensions, checks the 5 MiB image / 256 KiB text limits, image signatures or strict UTF-8 text, and recomputes the versioned SHA-256 digest before storage. The browser requires an explicit upload click and public-content acknowledgement. Content is publicly retrievable by reference; users must not upload private data. SHA-256 binds bytes and normalized media type but does not prove authorship, ownership, originality, or permanence.
- Content is stored as bytes plus a metadata sidecar. Reads recompute the content digest before serving it. The local adapter is single-process development storage. The hosted adapter uses Supabase service-role credentials only on the server; its content bucket is intentionally public. Credentials must never use `NEXT_PUBLIC_` variables. The repository migration enables row-level security and grants database access to service_role. Hosted-provider behavior requires configuration and was not verified against a Supabase account in this run.
- The activity synchronizer is pinned to chain ID 10143 and the validated deployment metadata. It waits five blocks, uses bounded block ranges and log batches, verifies successful receipts and exact receipt logs, persists unique transaction/log keys, and retries without advancing the cursor on RPC/receipt errors. A bounded cursor rewind handles detected block-hash changes. Confirmed entries are distinct from transient wallet submissions.
- The activity sync route is server-accessible and throttled per running process, but no authentication, distributed rate limiting, or continuously running worker is implemented. Deployments should apply hosting-level request limits and invoke it via the live feed. Local file storage is not suitable for multi-instance hosting; use the hosted adapter for shared persistent records.
- Upload endpoint body handling relies on the hosting runtime honoring the declared request-length check and framework request limits; the file is independently checked after multipart parsing. Configure a request-body cap near 5.2 MiB at the hosting edge. Content upload rate limiting and malware scanning are not provided.

## Residual risks / not verified

- The owner remains trusted to pause the protocol, change the tip fee up to 5%, transfer ownership, and direct protocol fees. The contract is immutable and has no recovery path for reward dust.
- Reward rounding strands small residual amounts. There is no dust sweep; this is conservative for solvency but may lock value indefinitely.
- No invariant handler or full stateful fuzz campaign has been added; the suite has one 256-run fuzzed payout invariant plus scenario tests. No professional independent audit has occurred.
- No deployment transaction, deployed-bytecode-to-source verification, wallet E2E, or actual live app write/read against a deployed hub has been performed.
- Server-side indexing uses the configured public RPC and a five-block confirmation buffer, and can be stale or unavailable. The application is not an authoritative chain explorer; receipt and RPC data remain provider-dependent.
- The synchronizer is client-triggered rather than a background worker, so history can be delayed while no client requests synchronization. Current app tests verify local persistence and validation; they do not verify provider uptime, Supabase availability, RPC reorg behavior on a live chain, malware safety, or production traffic controls.
- Slither/Foundry warnings remain for timestamps, supporter rounding, and external ETH call semantics; their impacts and evidence are recorded above. Do not treat warning count as a security guarantee.
