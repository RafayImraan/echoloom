# Content storage and persistent activity

## Content uploads

Users explicitly choose a file, review the public-content notice, and click Upload before any bytes leave the browser. Supported files are PNG, JPEG, WebP, and GIF images up to 5 MiB, plus UTF-8 plain text or Markdown up to 256 KiB. SVG and other active formats are rejected. The server independently validates filename, extension, MIME type, size, basic image signatures or text encoding, and recomputes the submitted digest before storing anything.

The digest is SHA-256 over the versioned envelope `UTF8("echoloom-content-v1\n" + normalized-MIME + "\n" + decimal-byte-length + "\n") || exact-file-bytes`. This binds the digest to the file bytes, media type, and length. It does not establish authorship, ownership, originality, safety, or permanence. Uploaded references are public; do not upload private or sensitive content.

The default `local` adapter persists content and metadata under `web/data/uploads` and activity under `web/data/activity.json`, surviving app restarts on that machine. Local content references are explicitly marked local-only and the publish button is disabled for them. Set `ECHOLOOM_DATA_DIR` to move the local data directory. The `supabase` adapter stores content in a public Supabase Storage bucket and activity/cursors in Postgres. Pinata mode uses Pinata only for uploaded content; confirmed activity and indexer cursors continue to use the local persistent store unless the separate Supabase mode is explicitly selected. For hosted public IPFS uploads, select `ECHOLOOM_STORAGE_DRIVER=pinata` and set server-only `PINATA_JWT` from a Pinata API key with **V3 Resources → Files → Write** permission (Admin is unnecessary). The app uses Pinata's V3 multipart upload endpoint with `network=public`, validates the returned CIDv1, attaches the SHA-256 digest, MIME type, byte size, and algorithm as file metadata, then retrieves the file through Pinata's public gateway and checks byte-for-byte equality before returning `ipfs://<CID>` for the existing contract. A timeout, gateway error, or content mismatch fails the upload response. The UI opens the content via Pinata's public gateway. Keep the JWT out of `NEXT_PUBLIC_*`, source control, and browser configuration. Create a Pinata account/API key yourself; no credentials are included, and account quotas/pricing may change. The Supabase option still requires applying `supabase/migrations/202610140001_echoloom_persistent_storage.sql` and setting `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` server-side.

For Pinata uploads, success means the provider accepted and pinned the file and returned a valid CID. The app displays `ipfs://<CID>` and the SHA-256 digest and fills the existing post form. Local-only URLs are rejected from on-chain publishing. A provider pin response does not guarantee every public gateway is immediately available, and pinning does not guarantee perpetual availability. The user must still submit a separate `createPost` transaction; a successful upload is not a blockchain transaction. EchoLoomHub already stores the URI and `bytes32` content hash, so no contract change or redeployment is required. A transaction receipt is reported only after the wallet transaction succeeds. The versioned SHA-256 digest is over the MIME/length envelope and exact file bytes; the IPFS CID is the provider's content-addressed identifier. Neither alone proves authorship, ownership, originality, or safety.

## Confirmed activity

The server-side indexer calls the configured Monad Testnet RPC (chain ID 10143), scans up to 2,000 blocks per refresh in RPC requests of at most 100 blocks, waits five blocks, and checks the block hash. It verifies each candidate event against a successful transaction receipt, receipt block, hub address, transaction sender, and exact receipt log before persistence. The unique key `(chain_id, hub_address, transaction_hash, log_index)` makes inserts idempotent. A changed cursor block hash causes a bounded rewind and removal of records after the rollback point. RPC errors leave the cursor unchanged for retry.

Persisted rows include chain, hub, transaction hash, block number/hash, log index, event type, wallet, Loom/post IDs and decoded event arguments where emitted. Only actual contract events are indexed; the contract does not emit a separate event for every conceivable UI action. Pending wallet submissions remain transient UI state and are not presented as confirmed activity. Activity API responses are capped at 100 rows and support offset, wallet, and Loom filters. The browser requests a bounded page from the server and does not use localStorage as event history.

The local adapter's JSON database is atomic-write persisted and serialized within one Node process; it retains the newest 50,000 event rows and should not be used by multiple local app processes against one directory. Supabase/Postgres is the shared hosted adapter with indexed, paginated database queries. Event polling is triggered by live-feed refreshes; this is not a continuously running hosted indexing worker. If the app is idle, new events appear when a client next requests synchronization. The RPC provider's availability and historical log limits remain external dependencies.

Sample content and sample feed entries remain clearly labeled local demo data and are not uploaded or represented as chain-confirmed records.
